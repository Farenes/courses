# Обзорный документ курсового проекта

## Введение

Проект рассчитан на 16 недель (около 4 месяцев) и должен иметь достаточный объем и сложность, чтобы допускать использование LLM в качестве инструмента, но не заменять собой самостоятельную работу студента по проектированию, реализации и проверке продукта.

## Общее описание системы

Под "системой" в данном контексте понимается не конкретный программный продукт (тема проекта выбирается студентом самостоятельно), а сквозной процесс выполнения курсового проекта: последовательность из семи связанных этапов, каждый из которых опирается на результаты предыдущего и формирует основу для следующего.

Логика движения по этапам устроена следующим образом:

1. Дизайн документ фиксирует, что за продукт разрабатывается, для кого и с какими требованиями — это отправная точка, на которую ссылаются все последующие этапы.
2. Аналитика переводит требования в детальное описание поведения системы: функции, диаграммы, сценарии.
3. Архитектура превращает описанное поведение в структуру: компоненты, контейнеры, классы и обоснованные технические решения.
4. Разработка реализует спроектированную структуру в виде работающего кода.
5. Тестирование проверяет, что реализованный код соответствует функциям и сценариям, зафиксированным на этапе аналитики.
6. Внедрение и поддержка переводят проверенный код в работающий и обновляемый продукт.
7. Документирование сводит результаты всех этапов в связный комплект документов для защиты и передачи продукта.

Каждый этап оформляется в виде отдельного документа с единой структурой: цель раздела, что требуется сделать, форма отчета, ожидаемый результат и критерии готовности. Такая структура позволяет проверять каждый этап независимо и одновременно видеть, как он связан с остальными.

## Что требуется сделать в целом

В рамках проекта в целом необходимо:

1. Сформулировать концепцию продукта и зафиксировать функциональные и нефункциональные требования к нему.
2. Детально проанализировать поведение системы: описать функции, построить диаграммы поведения (use case, sequence, activity, state) и описать пользовательские сценарии.
3. Спроектировать архитектуру продукта: построить C4-диаграммы, диаграмму классов и обосновать ключевые технические решения.
4. Реализовать продукт в коде в соответствии с приоритетами функций и принятой архитектурой, соблюдая единые стандарты качества кода.
5. Проверить продукт unit- и end-to-end тестами, а также описанными вручную тестовыми сценариями.
6. Настроить автоматизированный процесс сборки и доставки (CI/CD) и развернуть продукт в тестовом и/или рабочем окружении с базовым мониторингом и понятным процессом поддержки.
7. Оформить итоговую документацию: пояснительную записку, презентацию и user guide для конечного пользователя.

Сквозные требования, которые должны соблюдаться на всех этапах:

1. Каждый этап должен опираться на результаты предыдущего и не противоречить им; при возникновении отклонений их нужно явно фиксировать и обосновывать.
2. Объем и глубина проработки на каждом этапе должны быть достаточными, чтобы результат нельзя было получить одним запросом к LLM без самостоятельного анализа и решений.
3. Результат каждого этапа должен быть оформлен в форме отчета, описанной в соответствующем документе, и пригоден для независимой проверки.
4. По каждому этапу должен вестись журнал использования LLM: какие запросы делались, что было сгенерировано и что переработано самостоятельно. Журнал позволяет проверить соблюдение требования 2 и лучше контролировать использование LLM в процессе работы над проектом; подробный формат описан в разделе "Что требуется сделать" каждого этапного документа.

## Краткий план

Ориентировочная последовательность работы над проектом на протяжении 16 недель:

1. Дизайн документ — формулировка концепции продукта и требований. Результат: дизайн документ.
2. Аналитика — детализация функций, диаграммы поведения, описание сценариев. Результат: диаграммы и сценарии.
3. Архитектура — проектирование структуры системы. Результат: C4-диаграммы и диаграмма классов.
4. Разработка — самый продолжительный этап, реализация продукта итеративными приращениями от обязательных функций к дополнительным. Результат: код проекта.
5. Тестирование — проверка реализованного функционала, может частично вестись параллельно с завершением разработки. Результат: тест-кейсы и код тестов.
6. Внедрение и поддержка — настройка CI/CD и рабочего окружения. Результат: настроенное окружение.
7. Документирование — сведение результатов всех этапов в итоговый комплект документов и подготовка к защите. Результат: пояснительная записка, презентация, user guide.

Этапы 1–3 формируют основу проекта и должны быть завершены и согласованы с преподавателем до начала активной разработки, поскольку ошибки на этих этапах дорого исправлять позже. Этапы 4–6 могут частично пересекаться по времени: тестирование и настройка окружения имеет смысл начинать по мере готовности первых реализованных функций, а не откладывать до полного завершения разработки. Этап 7 логично начинать заранее в виде черновика, постепенно дополняя его по ходу проекта, и завершать в самом конце, когда все результаты уже получены.

## Календарный план по неделям

Проект рассчитан на 16 недель (около 4 месяцев). Контрольная точка назначается каждые 2 недели: к этому моменту студент должен показать научному руководителю конкретный проверяемый результат по одному или нескольким этапам. Поскольку разработка — самый объемный этап, ей отведено несколько последовательных контрольных точек с нарастающим результатом (приращениями функций), а не одна; остальным этапам, как правило, достаточно одной контрольной точки на 2 недели. Из-за ограниченного количества недель этапы 5–7 частично совмещены с соседними: тестирование стартует вместе с доработкой дополнительных функций, а внедрение — вместе с черновиком документации. Даты внутри плана ориентировочные и могут быть скорректированы по согласованию с научным руководителем, но сам ритм — раз в 2 недели — должен соблюдаться.

| № КТ | Недели | Этап(ы) | Что показать научному руководителю |
|------|--------|---------|--------------------------------------|
| КТ1 | 1–2 | 1. Дизайн документ | Готовый дизайн документ: концепция, функциональные и нефункциональные требования. |
| КТ2 | 3–4 | 2. Аналитика | Диаграммы поведения (use case, sequence, activity, state) и текстовые сценарии для всех обязательных функций. |
| КТ3 | 5–6 | 3. Архитектура | C4-диаграммы (Context, Container, Component), диаграмма классов, обоснование архитектурных решений. |
| КТ4 | 7–8 | 4. Разработка (приращение 1) | Настроенный репозиторий, CI-заготовка, первая часть обязательных функций (MVP-ядро) в рабочем виде. |
| КТ5 | 9–10 | 4. Разработка (приращение 2) | Все обязательные функции реализованы и работают согласно сценариям аналитики. |
| КТ6 | 11–12 | 4. Разработка (доп. функции) + 5. Тестирование | Желательные/дополнительные функции по возможности; unit- и e2e-тесты, тестовые сценарии, сводка покрытия функций тестами. |
| КТ7 | 13–14 | 6. Внедрение и поддержка + 7. Документирование (черновик) | Настроенные CI/CD, тестовое/рабочее окружение, базовый мониторинг; черновик пояснительной записки и user guide, сверенный с фактическим состоянием кода. |
| КТ8 | 15–16 | 7. Документирование (финал) | Итоговая пояснительная записка, презентация, user guide; репетиция защиты. |

Если фактический темп работы над проектом отличается от плана (например, тема оказалась сложнее или проще ожидаемого), контрольные точки можно сдвигать, но интервал между ними не должен превышать 2 недель без явного согласования с научным руководителем — это позволяет вовремя заметить отставание и не откладывать всю проверку результата на конец семестра.
